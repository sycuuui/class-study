**요구사항 정리(명시 요구사항)**

**기능 요구사항 체크리스트**
- [ ] 학생 목록 조회 API 제공
- [ ] 강좌 목록 조회 API 제공
- [ ] 강좌 목록 조회 시 전체/학과별 조회 지원
- [ ] 강좌 목록 응답에 정원/현재 인원/시간 정보 포함
- [ ] 교수 목록 조회 API 제공
- [ ] 수강신청 API 제공
- [ ] 수강취소 API 제공
- [ ] 내 시간표(이번 학기) 조회 API 제공
- [ ] 학생당 최대 18학점 제한 적용
- [ ] 동일 시간대 중복 수강 불가
- [ ] API 문서 제공(프론트 연동 목적)

**비기능 요구사항 체크리스트**
- [ ] 서버 사이드만 구현(프론트 제외)
- [ ] GET /health 가 200을 반환하는 시점에 API 호출 가능해야 함
- [ ] 서버 시작 후 1분 이내에 데이터 생성 및 헬스체크 완료
- [ ] 데이터는 애플리케이션 실행 시 프로그래밍 로직으로 동적 생성
- [ ] 정적 파일(SQL, CSV) 및 대량 리터럴 데이터 사용 금지
- [ ] 현실적인 데이터(의미 없는 이름 지양, 실제 대학에서 사용할 법한 이름/패턴)
- [ ] 과도한 수준의 외부 데이터 크롤링/통계 기반 생성 불필요
- [ ] 데이터는 비즈니스 규칙 위반 없이 생성되어야 함
- [ ] 목록 조회 API로 유효한 ID 확인 가능해야 함(평가자 테스트 편의성)

**동시성 관련 요구사항 체크리스트**
- [ ] 정원이 1명 남은 강좌에 100명 동시 신청 시 정확히 1명만 성공
- [ ] 어떠한 경우에도 정원 초과 신청 불가

**동시성 제어 전략(문서 보강)**
- 인메모리 환경에서 정원 초과를 막기 위해 **강좌별 Lock**을 사용한다.
- (가능하면) **학생별 Lock**을 추가해 동일 학생의 동시 요청(중복 신청/취소 충돌)을 직렬화한다.
- 데드락 회피를 위해 **락 획득 순서를 고정**한다.
  - 예: `(courseId → studentId)` 순서로만 락 획득
- 수강신청/수강취소에서 **원자적으로 보호되는 임계구역**:
  - 수강신청: ID 유효성 확인 → 중복 신청 확인 → 정원 확인 → 신청 등록/카운트 증가
  - 수강취소: ID 유효성 확인 → 신청 존재 확인 → 신청 삭제/카운트 감소
  - 수강신청 임계구역(락 내부): 중복 신청 확인 → 정원 확인 → enrolled 갱신 → enrollment 저장
- 락 외부(사전 검증): 요청 파라미터 검증, 학생/강좌 존재 확인(단, 최종 상태 일관성은 락 내부에서 재확인 가능)
- 실패 응답 정책 및 매핑(HTTP status + error code + alias):
  - 요청 파라미터/바디 유효성 오류: 400 + 500 (`INVALID_REQUEST`)
  - 학생 없음: 404 + 501 (`STUDENT_NOT_FOUND`)
  - 강좌 없음: 404 + 502 (`COURSE_NOT_FOUND`)
  - 교수 없음: 404 + 503 (`PROFESSOR_NOT_FOUND`)
  - 수강신청 내역 없음: 404 + 504 (`ENROLLMENT_NOT_FOUND`)
  - 정원 초과: 409 + 600 (`CAPACITY_EXCEEDED`)
  - 중복 신청: 409 + 603 (`DUPLICATE_ENROLLMENT`)
  - 학점 초과: 409 + 601 (`CREDIT_LIMIT_EXCEEDED`) (TODO)
  - 시간 충돌: 409 + 602 (`TIME_CONFLICT`) (TODO)
  - 서비스 준비 중: 503 + 700 (alias 없음)
- 안전성 근거:
  - 강좌별 Lock으로 **정원 확인과 등록을 단일 임계구역**으로 묶어 동시성 경쟁 조건을 차단한다.
  - 고정된 락 순서와 학생별 Lock을 결합해 **데드락 없이** 동시 요청을 직렬화할 수 있다.
  - 100명 동시 신청 시에도 **정원 갱신이 단일 순서로 처리**되므로, 정원 초과가 발생하지 않는다.

**데이터 생성/초기화 요구사항 체크리스트**
- [ ] 서버 시작 시 테스트용 초기 데이터가 준비되어야 함
- [ ] 데이터 생성 완료 후에만 헬스체크 200 응답
- [ ] 데이터 생성은 1분 이내 완료
- [ ] 최소 데이터 규모: 학과 10개 이상
- [ ] 최소 데이터 규모: 강좌 500개 이상
- [ ] 최소 데이터 규모: 학생 10,000명 이상
- [ ] 최소 데이터 규모: 교수 100명 이상
- [ ] 데이터는 런타임에 생성(정적 파일 금지)
- [ ] 소규모 토큰 목록(이름/학과명 등)은 코드 포함 가능
- [ ] 완성된 레코드 단위 데이터는 런타임 생성
- [ ] 강좌 목록 응답 필수 필드 포함
- [ ] 강좌 목록 필드: id, name, credits, capacity, enrolled, schedule
- [ ] 필드명 표기 규칙은 자유(camelCase, snake_case, 한글 모두 허용)

**명시되지 않았지만 합리적 결정이 필요한 항목(결정 사항)**
1. API 형식
선택지 A: REST + JSON
선택지 B: GraphQL
추천안: REST + JSON
근거: 프론트 연동과 목록 조회 중심 요구에 적합하며 구현/문서화가 단순함

2. 인증/식별 방식
선택지 A: 인증 없음, 요청에 studentId를 포함
선택지 B: 토큰 기반 인증
추천안: 인증 없음, 요청에 studentId 포함
근거: 요구사항에 인증이 없고 과제 범위에서 동시성/규칙 검증이 핵심

3. “이번 학기” 범위
선택지 A: 단일 활성 학기만 지원
선택지 B: 다학기(과거/미래) 지원
추천안: 단일 활성 학기만 지원
근거: 요구사항에 이번 학기만 명시, 범위를 축소해 핵심 기능 집중

4. 수강신청 중복 처리
선택지 A: 동일 강좌 재신청은 실패
선택지 B: 동일 강좌 재신청은 멱등 성공
추천안: 멱등 성공
근거: 클라이언트 재시도에 안전하고 사용자 경험 개선

5. 수강취소 정책
선택지 A: 수강 중인 강좌만 취소 가능
선택지 B: 미신청 강좌 취소 요청을 멱등 성공 처리
추천안: 수강 중인 강좌만 취소 가능
근거: 명확한 피드백 제공이 필요하고 데이터 정합성 점검에 유리

6. 응답 코드/에러 표현
선택지 A: HTTP 상태코드 + 오류 코드 문자열
선택지 B: 항상 200 + 에러 필드
추천안: HTTP 상태코드 + 오류 코드 문자열
근거: 표준적인 API 문서화 및 클라이언트 처리 용이

7. 강좌 시간표 형식
선택지 A: 문자열(예: "월 09:00-10:30")
선택지 B: 구조화 배열(요일, 시작, 종료)
추천안: 문자열 유지 + 내부 구조화
근거: 요구사항 예시에 부합하면서 검증 로직은 구조화로 처리 가능

8. 데이터 생성 시 난수 시드
선택지 A: 고정 시드(재현 가능)
선택지 B: 매 실행 랜덤 시드
추천안: 고정 시드
근거: 테스트 재현성과 디버깅 용이성 확보

9. ID 체계
선택지 A: 정수 증가 ID
선택지 B: UUID
추천안: 정수 증가 ID
근거: 목록 조회 및 평가자 확인 편의성

10. 강좌 정원 기본값
선택지 A: 고정 범위(예: 20~40) 랜덤
선택지 B: 모든 강좌 동일 정원
추천안: 고정 범위 랜덤
근거: 현실적인 데이터와 동시성 테스트 다양성 확보
